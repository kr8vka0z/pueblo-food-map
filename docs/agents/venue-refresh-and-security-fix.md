# Venue website reader and daily security fix

Moved verbatim from AGENTS.md. The hard rules stay in AGENTS.md.

## Venue website reader (refresh pipeline)

- **The venue website reader (`--only website`, `scripts/refresh/website.ts`) runs only on the server** (`ops/systemd/`, weekly, from a clean `origin/main` checkout), never in GitHub Actions: Gemini is `agy` under Kyle's login there, and this repo is public. Gemini only reads text our code fetched; a field counts only if its quote is on our copy of the page. Page text is untrusted: never give `agy` a file path or a working directory with files in it, and never start it with any `CLOUDFLARE_*`/`OP_*` variable (`untrustedChildEnv`) or let the token touch disk past startup (`PFM_SECRETS_FILE`, read and deleted by `refresh-ingest.ts`). Page fetches go only to public addresses (`makePinnedLookup`, every redirect hop) and never through a browser, which would follow redirects we can't check. Only the prompt asks it not to search outside website discovery; nothing enforces that, which is why every claim is checked against our own fetched text. Model: `PFM_GEMINI_MODEL`, default `gemini-3.8-flash-medium` (Argon's quota is small and shared). A Gemini failure aborts the source with zero writes; a failed page never means closed. Real runs against staging: `--db-mode staging --only website` (needs migration `0025` there).

## Auto-apply rules

- Date-only updates auto-apply and never touch `venues` (a fetch is not a confirmation; `last_verified` moves only on a human approve or edit). The one other automatic write is the source switch (`src/lib/sourceSwitch.ts`): a `care_and_share` or `website` (source, field) pair (never `website` `url`) applies its own plain changes after Kyle approved 5 in a row unedited — never adds, removals, clears, or `needs_review`/unconfirmed-match cards, and it doesn't move `last_verified`. A field the venue told us (a `venue_direct` pin in `venue_observations`) never auto-applies through any lane. `REFRESH_AI_AUTO_APPLY` stays `"false"` until Kyle has checked a watched run's triage lanes against real decisions.

## Daily security fix (`security-fix.yml`)

- **Daily security fix (`security-fix.yml`, about 17:00 UTC, GitHub Actions, not a Worker cron):** patches production dependencies in `package-lock.json` on `dev` through an auto-merging `fix/security-advisories` PR. That branch is bot-owned and force-pushed every run: never push to it. Build-tool-only advisories are not auto-fixed (weekly Dependabot version updates cover them). If an open issue titled "Security check is failing and cannot be fixed automatically" exists, dev's own lockfile fails the required "Dependency CVE Audit" check and every PR into `dev` is blocked; the usual cause is an exact-pinned direct dependency that Monday's Dependabot update normally bumps, and the issue carries the hand-fix recipe. Dependabot *security* updates stay OFF on purpose: that is a repo setting, invisible in diffs, so do not re-enable it. An advisory published after Saturday's cut turns the open release PR red: close it and re-run `release.yml` once `dev` is fixed. Like `release.yml`, it runs from `main`'s copy, so an edit takes effect only after it reaches `main`.
